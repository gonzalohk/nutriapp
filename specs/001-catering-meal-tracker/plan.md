# Implementation Plan: Catering Meal Tracker

**Branch**: `001-catering-meal-tracker` | **Date**: 2026-10-03 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/001-catering-meal-tracker/spec.md`

## Summary

A mobile-first, installable web app where a family records, per person and per day, what
happened to each catering meal (picked up, cancelled, not picked up, permission), with optional
compressed photo proof, exact monthly counters, history, reports and export.

Technical approach (details in [research.md](research.md)): a static React + TypeScript + Vite
single-page app styled with Tailwind, talking directly to Supabase (PostgreSQL with Row Level
Security, Auth, private Storage). Business rules on dates live in one pure, timezone-safe domain
module; the database re-checks the hard invariants (no duplicate meal, no weekend or holiday
meal). Bolivian holidays are generated by rule with `date-holidays` at seed time and stored as
editable data. Photos are compressed on the device (WebP with JPEG fallback, 1600 px, 500 KB
cap) with a thumbnail, and stored privately. A small offline outbox covers poor connections.
Hosting is a free static host. No custom server.

## Technical Context

**Language/Version**: TypeScript 5.x (strict), Node.js 22 for tooling; SQL (PostgreSQL 15+ via Supabase)

**Primary Dependencies**: React 19, Vite, Tailwind CSS, `@supabase/supabase-js`, TanStack Query (+ IndexedDB persistence), wouter (routing), `vite-plugin-pwa` (Workbox), `fflate` (lazy-loaded ZIP). Build-time only: `date-holidays`

**Storage**: Supabase PostgreSQL (data) and Supabase Storage private bucket (photos); IndexedDB on the device for cache and outbox

**Testing**: Vitest (domain/unit, run under three `TZ` values), database tests as Vitest suites on PGlite, an embedded Postgres that applies the real migrations without Docker (constraints, triggers, RLS); integration tests that run the app's data layer against a real PostgreSQL and PostgREST (no Docker), Playwright (mobile viewport e2e)

**Target Platform**: Modern mobile browsers (Android Chrome, iOS Safari 16.4+) as an installable PWA; desktop browsers for secondary use

**Project Type**: Web application (static SPA + managed backend), single repository

**Performance Goals**: Record an outcome in < 10 s (no photo) / < 20 s (photo); month detail with thumbnails visible in < 2 s on a typical mobile connection

**Constraints**: Free tiers only (Supabase Free: 500 MB DB, 1 GB storage; free static host); startup JS ≤ 160 KB gzip (measured 153 KB; raised from the initial 150 KB estimate because `supabase-js` alone is 55 KB, see research R2); photo ≤ 500 KB, thumbnail ≤ 40 KB; offline view and queued writes; UI language Spanish by default; all dates in `America/La_Paz`

**Scale/Scope**: One household, up to about 10 people and a few adult users; ~80 meals/month for four people; 4 primary tabs, about 10 screens

**Structure Decision**: A single repository with one deployable app and a `supabase/` folder for
schema and tests. `src/domain` is deliberately free of browser and network code so the calendar
rules, the most error-prone part of the product, are testable in milliseconds and independent of
the framework. Feature folders keep screens, hooks and local components together.

## Implementation Phases

Ordered for incremental, independently testable delivery (maps to spec priorities):

1. **Foundation**: repo scaffold, tooling, Tailwind, i18n, Supabase local, CI, migrations for
   households/auth/RLS, login/setup/join flow.
2. **Calendar core (US2)**: plain-date and Bolivia-time helpers, calendar module, holiday
   generation script and seed, `meals_validate_date`, `apply_month_plan`, month generation UI.
3. **Quick record (US1)**: Today screen, `set_meal_status`, status log trigger, optimistic UI.
4. **Counters (US3)**: `monthly_stats`, Month screen counters and warnings.
5. **Photos (US1 photo step, US5)**: compression pipeline, thumbnails, private bucket and
   policies, upload, signed URLs, viewer, delete.
6. **People and plans (US4, US6)**: people CRUD, plan terms, holiday and exceptional-date
   management, reconcile flow.
7. **History and calendar polish (US5)**: year list, month detail, photo thumbnails.
8. **Export, report, backup (US7)**: CSV, photo ZIP, printable report, backup workflow, restore docs.
9. **Offline and PWA (US8)**: manifest, service worker, persisted query cache, outbox, sync indicators.
10. **Hardening**: timezone test matrix, e2e, accessibility pass, performance budget check,
    README and deployment docs, licenses file, analyze/consistency review.

Notifications are explicitly deferred (research R10).

## Risks

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Holiday data misses a decree or a regional holiday | Meal on a holiday or missing meal | Household overrides; holiday list screen shows source; tests pin 2026 and 2027 outputs |
| Timezone/date off-by-one | Wrong day for a meal | Plain-date strings, `date` columns, test matrix under three `TZ` values |
| Supabase Free pauses after 1 week idle | App unavailable after a long break | Weekly keep-alive job; documented resume step |
| No automatic backups on Free | Data loss | Weekly dump, CSV and photo export, restore guide |
| Safari lacks WebP encoding via canvas | Larger photos | JPEG fallback checked by produced MIME type; size-fit loop |
| 1 GB photo storage fills in ~3 years | Uploads fail | Capacity estimate, quality constants, export-and-archive path, R2 as escape hatch |
| iOS offline limits (no background sync) | Queue flushes only when the app is open | Flush on foreground/online events; clear "pending sync" indicators |
| Open sign-up on the hosted project | Quota use by strangers | Accounts without a household see no data; household creation is closed after the first one; captcha can be added later |
| Photo legibility at the chosen compression | Unreadable receipts | Validate on real photos early (task in phase 5), tune constants in one file |

## Complexity Tracking

| Item | Why Needed | Simpler Alternative Rejected Because |
|------|------------|-------------------------------------|
| Offline outbox in IndexedDB | Spec FR-037 and the user's poor-connection requirement: statuses and photos must survive loss of signal | Online-only is simpler but loses a recorded meal when the signal drops at pickup time |
| Database triggers re-checking weekend/holiday | RULE-013/014 must hold even if a client bug or a direct call writes a bad date | Client-only validation cannot protect the data; the check is only a few lines of SQL and does not duplicate selection logic |
